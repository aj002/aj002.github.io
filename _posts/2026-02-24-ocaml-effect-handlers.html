OCaml effect handlers, with one example

Which functions need to change when a query becomes asynchronous?

A database query starts returning a promise. Which functions have to change? It depends on where the result is used. A function that only passes the promise on may need no edit at all.

This is a small example of the problem discussed in Bob Nystrom’s What Color is Your Function? OCaml’s effect handlers offer another way to suspend a computation while keeping its callers in ordinary function-call style.

Start with JavaScript

Assume the query initially returns an array:

Before: synchronous query
function renderDashboard() {
  const data = processData(getMetrics());
  return formatChart(data);
}

function processData(raw) {
  return raw.filter(valid).map(normalize);
}

function getMetrics() {
  return db.query("SELECT * FROM metrics");
}

Once db.query returns a promise, getMetrics can forward it unchanged. renderDashboard needs the array before it can process it, so this version adds an await there:

After: query returns a promise
async function renderDashboard() {
  const raw = await getMetrics();
  return formatChart(processData(raw));
}

function getMetrics() {
  return db.query("SELECT * FROM metrics");
}

// processData is unchanged.

processData still takes an array and returns an array. It does not call getMetrics. The caller of renderDashboard now receives a promise too, so it must arrange to use the chart after resolution. It can use await, return the promise, or attach a callback.

Some interfaces make this awkward. A synchronous sort comparator cannot wait for a network request. One option is to fetch the sort keys first, then run the ordinary sort.

A request and a handler

In OCaml, Effect.perform suspends a computation and passes an operation to an enclosing handler. The handler receives a continuation, which represents the suspended computation. Calling Effect.Deep.continue resumes it with a value.

This example requests a list of integers. The handler supplies a fixed list, so no network service is needed:

OCaml 5: supply data through a handler
type _ Effect.t += Read_metrics : int list Effect.t

let get_metrics () = Effect.perform Read_metrics

let process_data raw =
  raw |> List.filter (fun x -> x > 0)
      |> List.map (fun x -> x * 2)

let render_dashboard () =
  get_metrics () |> process_data
                 |> List.map string_of_int
                 |> String.concat ", "

let run_with_metrics metrics f =
  Effect.Deep.try_with f ()
    { effc = fun (type a) (eff : a Effect.t) ->
        match eff with
        | Read_metrics ->
            Some (fun (k : (a, _) Effect.Deep.continuation) ->
              Effect.Deep.continue k metrics)
        | _ -> None }

let () =
  print_endline (run_with_metrics [0; 2; 3] render_dashboard)
(* Prints: 4, 6 *)

Read_metrics is declared to return an int list. When the handler supplies [0; 2; 3], execution resumes inside get_metrics. The remaining calls filter out zero, double the values, and format the result.

Where asynchronous I/O fits

The example resumes immediately. An I/O scheduler can instead retain the continuation, run another task, and resume the first one when its data arrives. That scheduler still has to manage readiness, errors, and cancellation. Putting a blocking HTTP call inside a handler would still block.

OCaml does not track these effects in function types. A missing handler is therefore a runtime problem: an unhandled operation raises Effect.Unhandled. The visible function signature alone will not tell you every way the call can suspend.

There is also a restriction on the continuation: OCaml’s continuations are one-shot. Resuming the same one twice raises Effect.Continuation_already_resumed. A search algorithm cannot explore two branches simply by continuing the same captured computation twice.

In this example, the handler lets the data source change while the processing functions keep the same interfaces. Whether that is worth using depends on the surrounding program: its scheduler and error handling still need to be understood.
